# Solver progress — 2026-10-17

## Текущее состояние

Основной Python solver находится в `solution/`; запуск описан в `solution/README.md`. Это статический анализатор Java/Spring поверх skeleton, сценариев и снимка SQL. Train Ticket и его сервисы не запускались; runtime traces не собирались. Rust-порт не начат: после этой итерации приоритет — качество рёбер, а не бонус языка.

`solution/ttsolver/catalog.py` связывает методы, call sites, типы, маршруты контроллеров и кандидатов skeleton с Java AST. `engine.py` исполняет достигнутые выражения и операторы, включая короткое замыкание, циклы, исключения, ветвления, конструкторы и вызовы; неизвестные условия исследуются несколькими путями. `adapters.py` моделирует Spring authentication/filter, HTTP `RestTemplate`, RabbitMQ, JPA и Java-библиотеки. `sql.py` загружает реальные строки снимка и поддерживает изменения между шагами. `planner.py` связывает сценарные действия с конкретными UI/API запросами и выбранными данными из ответов; `events.py` допускает только рёбра, разрешённые skeleton. События хранят происхождение и объяснение в `--diagnostics`.

## Измерения

Команда `python platform/evaluate_golden.py gold/S0.json solution/output/answer.json` дала **S0 IoU 0.990** (среднее четырёх отношений): `executes` 34/34, `calls` 23/24, `remote` 0/0, `data` 7/7. FP на S0 нет; единственный FN — `TokenServiceImpl#getToken → User#getPassword`. В `TokenServiceImpl#getToken` прямого вызова `User#getPassword` нет; `AuthenticationManager` вызывает его как Spring callback. Добавление этого ребра вручную повысило бы S0, но нарушило бы общую модель call-site-sensitive `calls` и могло бы создать FP на скрытых сценариях. Этот конфликт требует проверки семантики золотого ребра при дальнейшем анализе.

Полный ответ S0–S7 проходит проверку формата `evaluate_golden.py`: отклонённых рёбер нет. Локальных gold для S1–S7 нет, их IoU неизвестен. В последнем полном прогоне (~86 с) число рёбер: S0 64, S1 482, S2 484, S3 432, S4 507, S5 613, S6 446, S7 429. S0–S4 и S6–S7 прошли без остановленных путей. В S5 один из семи путей исключён из пересечения как несовместимый с явным выбором найденного поезда; шесть продолжаются. Это диагностическая эвристика, которую надо отдельно проверять против других формулировок сценариев.

## Известные ограничения и риски

1. Текстовый planner рассчитан на предоставленные сценарии и типовые перефразировки; произвольный natural language без уточняющих данных может дать неверный endpoint или DTO. Конкретные неописанные UI-значения представлены `Unknown`, но часть значений (учётные данные, дата исполнения, первый контакт/поезд) выбрана из контекста или текста сценария.
2. Ветвление ограничено `--max-paths` (по умолчанию 8). При исчерпании бюджета путь останавливается с диагностикой и не превращается в широкий graph closure. Пересечение путей может пропустить действительно выполненное ребро, если неопределённость не разрешена наблюдением сценария.
3. Модели внешнего HTTP, Spring, ORM и Jackson приближённые. Статический снимок не задаёт поведение реального внешнего платёжного провайдера, времени, случайных мест, транзакционных откатов и побочных эффектов вне сохранённых сервисов. Часть HTTP-ответов получает обычный `202 ACCEPTED` согласно контроллерам; это требует сверки при иных annotations.
4. В S5 обработка расширенного поиска дорогая: повторный проход по нескольким вариантам маршрута увеличивает время и число потенциальных рёбер. Пересечение путей предотвращает часть FP, но без hidden gold невозможно доказать точность этих 613 рёбер.
5. Наблюдения `S0` и исходный Java-код расходятся в одном `calls`-ребре. Не добавлять его без общего объяснения Spring callback semantics и проверки влияния на другие сценарии.

## Следующий приоритет

1. Проверить скрытые сценарии по доступной команде платформы; сохранить per-relation TP/FP/FN и привязать ошибки к событиям provenance.
2. Улучшить наблюдательную фильтрацию альтернатив и точность выбора UI/DTO без специальных правил для ID сценария.
3. Сверить Spring callback и JPA collection semantics для оставшегося FN и возможных скрытых FP.
4. Профилировать S5, убрать повторные вычисления и по возможности снизить время полного прогона.
5. Рассматривать Rust только после стабилизации качества Python solver и оценки стоимости порта на реальных метриках.
