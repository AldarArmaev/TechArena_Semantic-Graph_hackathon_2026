# TechArena. Семантический граф микросервисной архитектуры

**Train Ticket** — учебный сайт продажи железнодорожных билетов. Поиск поездов, оформление заказов, оплата, страховка и другие действия здесь распределены между 41 Java-сервисом. Каждый микросервис отвечает за свою часть работы и при необходимости общается с другими по сети.

Представьте, что пассажир покупает билет без страховки. В коде есть возможность обратиться к сервису страховки, и заранее подготовленный граф проекта показывает эту **возможную** связь. Но в таком сценарии пассажир страховку не выбрал — значит, обращения не будет.

Ваша задача — написать программу, которая по описанию действий пользователя, исходному коду и графу **без запуска Train Ticket** предскажет, какие методы выполнятся, какие вызовы между методами и сервисами произойдут и к каким таблицам обратится код. Нужно учитывать входные данные, исходное состояние системы и последствия предыдущих действий. Ответом будет JSON со связями для каждого сценария.

 Вся идея челленджа заключается в **легковесном** анализаторе кода, который будет помогать LLM-агентам разбираться в микросервисных проектах, локализовать баги и реализовывать новый функционал.
## Что вам дано

- `targets/trainticket/` — исходники именно той версии проекта, по которой подготовлены правильные ответы. Здесь же находится код веб-интерфейса `ts-ui-dashboard/`.
- `skeleton/trainticket.json.gz` — предварительный граф проекта (так называемый "скелет"). В нём есть вершины для методов, мест вызовов, настроек и таблиц, а также связи, которые **могут** сработать. Граф не знает, какие условия выполнит конкретный пользователь, и не содержит всех нужных ответов.
- `scenarios/` — описания действий пользователя на английском языке. Один шаг сценария соответствует одному запросу через шлюз. Готовые адреса запросов и тела в описании не указаны: найдите соответствующие действия в коде веб-интерфейса и серверах.
- `context/` — исходное состояние баз данных, учётная запись, дата и другие условия. Все сценарии начинаются с одного и того же состояния, но **внутри** сценария каждый шаг может повлиять на следующий.
- `scenarios/S0.json` и `gold/S0.json` — открытый пример и правильный ответ к нему. Ещё для семи сценариев правильные ответы скрыты.

Читать и компилировать исходники, применять статический анализ, текстовый поиск и модели машинного обучения можно; учиться на открытом S0 (`gold/S0.json`, `context/`) — можно. Запускать Train Ticket или его отдельные сервисы, собирать трассы исполнения и использовать самостоятельно собранные рантайм-данные по проекту нельзя. Код решения прилагается к сдаче на платформе (она принимает файлы); после соревнования мы перезапускаем и проверяем код лучших решений.

## Как использовать граф

Файл содержит `nodes` (вершины) и `edges` (связи). У каждой вершины есть точный идентификатор и поле `kind`, показывающее её вид. Определяйте вид по `kind`, а в ответ **копируйте идентификатор целиком из `nodes`**: сокращения и придуманные идентификаторы методов или таблиц не принимаются.

Связи графа-скелета помогают найти возможный путь: кого метод может вызвать, в какой сервис может уйти запрос и к какой таблице может обратиться код. Для этого пригодятся, в частности, `calls`, `runtime_dispatch`, `remote_call`, `message_delivery` и `data_access`. Но наличие такой связи ещё не означает, что она сработает при данных этого сценария. Некоторые вызовы придётся уточнить по исходникам.

Граф-скелет — **подсказка, а не готовый ответ**. Например, в нём `calls` может идти от конкретного места вызова к возможному методу. В вашем ответе `calls` соединяет *вызывающий метод* с тем *методом, который действительно выполнился*. Вызывающий метод можно найти в поле `method` вершины `call_site`.

## Что отправлять

Ответ — **один JSON-файл на все сценарии**: поле `project` и словарь `scenarios`, где ключ — идентификатор сценария, а значение — объект со списком рёбер `edges`. Каждое ребро задаётся полями `source`, `relation`, `target`. В скелете вид связи обозначен полем `type`; **в вашем ответе нужно поле `relation`**. Решение одно — программа, которая по тексту любого сценария строит его блок; сценариев в файле столько, сколько выдано (S0–S7).

Пример (по одному ребру на сценарий, чтобы показать структуру):

```json
{
  "project": "trainticket",
  "scenarios": {
    "S0": {
      "edges": [
        {
          "source": "scenario:S0",
          "relation": "executes",
          "target": "method:ts-auth-service:auth.controller.UserController#getToken(auth.dto.BasicAuthDto,org.springframework.http.HttpHeaders)"
        }
      ]
    },
    "S1": {"edges": ["…"]},
    "S7": {"edges": ["…"]}
  }
}
```

`scenario:S0` — служебный идентификатор для ответа; его нет среди вершин скелета. Для остальных концов рёбер используйте существующие идентификаторы **методов** и **таблиц**. Нужно указывать один из четырех видов связей:

| `relation` | Откуда → куда | Когда добавлять |
| --- | --- | --- |
| `executes` | сценарий → метод | Метод проекта выполнился хотя бы раз. |
| `calls` | метод → метод | Первый метод вызвал второй. При вызове через интерфейс укажите выполнившуюся реализацию. |
| `remote` | метод → метод другого сервиса | Из одного сервиса ушёл запрос или сообщение, и его обработал метод другого сервиса. |
| `data` | метод → таблица | Из метода ушёл SQL к этой таблице. Источник ребра — метод, в котором стоит вызов репозитория, а не обработчик выше по стеку; SQL, который ORM выполняет позже (при фиксации транзакции), относится к тому же методу. |

Ответ описывает **весь сценарий**, а не отдельные шаги: порядок и количество повторений не нужны, одинаковое ребро указывают один раз. Если действие закончилось ошибкой, учитывайте код, успевший выполниться до отказа. Исполняемые строки и новые вершины добавлять не нужно.

Считаются методы самого проекта, включая проектные фильтры, и таблицы, к которым реально обратился SQL. Каждая таблица, к которой ушёл SQL, — отдельное ребро; таблицы коллекций сущностей (`user_roles`, `route_stations`…) ORM читает отдельными запросами, и они — отдельные вершины. Методы библиотек и сгенерированные геттеры, которые библиотека вызвала через отражение, в ответ не включаются. Работа фреймворка тоже не превращается автоматически в `calls` между двумя методами проекта: такое ребро ставьте, только когда первый метод действительно вызывает второй.

## Как оценивается результат

Мы будем сравнивать предложенные вами рёбра графа с правильными отдельно для каждого сценария и каждого из четырёх видов связи. Результат за вид — **число совпавших рёбер, делённое на число всех разных рёбер в вашем ответе и эталоне вместе** (IoU). Лишние рёбра снижают балл так же, как пропущенные. Если и у вас, и в эталоне рёбер данного вида нет, за него начисляется 1; если в эталоне рёбер нет, а вы добавили хотя бы одно, начисляется 0.

Балл за сценарий — среднее по четырём видам связей. Итог — среднее по семи сценариям со скрытыми ответами. Если в файле нет блока для одного из них, за этот сценарий начисляется 0. Открытый S0 нужен для разработки, но **в итоговый балл не входит** (его блок в файле не мешает). Сдавать файл можно много раз; в зачёт идёт последняя принятая сдача целиком.

**Надбавка за Rust.** Решения, в которых анализ кода и построение ответа реализованы на Rust, получают надбавку **10 %** к итоговому баллу: итог × 1,10, но не выше 1,0. Надбавка начисляется после проверки кода: приложите код решения к финальной сдаче на платформе, организаторы убеждаются, что сданные ответы получены этим кодом. Тонкая обёртка на Rust вокруг решения на другом языке или вокруг программ-примеров из пакета надбавку не получает. Во время соревнования лидерборд показывает баллы без надбавки; она применяется в итоговом ранжировании.

## С чего начать

В пакете есть небольшие программы-примеры `platform/baseline_*.py`. Их можно изучать и улучшать; обязательного способа решения нет. Например, запустите программу, которая сопоставляет описание действий с кодом веб-интерфейса, на всех сценариях сразу, а затем проверьте её ответ:

```bash
python3 platform/baseline_nlp.py skeleton/trainticket.json.gz targets/trainticket scenarios/*.json -o my-answer.json --explain
python3 platform/evaluate_golden.py gold/S0.json my-answer.json
```

`--explain` показывает, какие входные методы программа выбрала для шагов каждого сценария. Проверка посчитает балл по S0 (его эталон есть) и для остальных сценариев проверит только формат — существование идентификаторов, отношения, виды вершин; это **не проверка того, что связь действительно сработает**. Готовые ответы всех трёх программ-примеров лежат в `examples/` — это образцы формата файла.

Правильный ответ для S0 лежит в `gold/S0.json`: он помогает проверить правила на настоящих идентификаторах и увидеть, какие части проекта затрагивает один сценарий.
